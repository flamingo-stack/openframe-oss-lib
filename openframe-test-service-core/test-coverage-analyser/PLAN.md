# test-coverage-analyser — API coverage gaps for the E2E suite

**Status:** milestone 0 (matrix + headless report, manual trigger) implemented and run on 2026-09-12;
the plan layer (scored backlog, mechanical known-gaps matching, run history) added 2026-09-13 and
seeded with the ten proposals of the first report. Milestones 1–3 are designed below and not built.
Sibling of `openframe-saas-shared/openframe/services/openframe-saas-test/test-results-analyser/`,
which analyses *failures*; this one analyses *absence*.

## Problem

`openframe-test-service-core` grew endpoint by endpoint from captured traffic. Nothing records what
the product exposes versus what the suite calls, so a new feature can ship through the UI with no
test touching its API and nobody notices until the nightly fails for an unrelated reason. Code
coverage tools do not apply: the suite runs against a deployed environment, not in-process.

The measurable unit here is the **API contract**: GraphQL root fields and REST mappings. They are
enumerable from source, the tests name them literally, and the dashboard app names them literally
too, which gives a denominator that reflects what users actually exercise instead of everything the
schema happens to declare.

## Goal

After any change to product, UI or tests, answer in one run:

1. which operations the UI uses that no test reaches (the gaps that matter first), ranked by how
   recently they appeared and by whether a whole area is uncovered;
2. which operations nobody uses or tests (API-only surface, to accept or cover deliberately);
3. what to write next: concrete, implementable test proposals in the suite's own conventions.

## Decisions

| Decision | Choice |
|---|---|
| Denominator | Product schemas + controllers at `origin/main` in the four repos; UI usage from `openframe-oss-frontend` at `origin/main` as the priority filter. `openframe-frontend-core` is a component library with no GraphQL and only hub REST paths, so it is not read. |
| Coverage credit | Any enabled `@Test` reaching the operation through the static call graph: direct, setup, base class, helper (transitive), client-to-client. Disabled tests never count. |
| Matching | GraphQL by root-field name; REST by method + normalised path after stripping the consumer's gateway prefix. Ambiguous matches are kept (all sources listed), never dropped. |
| Two-stage output | Deterministic matrix (`coverage_matrix.py`, stdlib only, ~25 s) that is correct on its own; then a headless Claude pass (`prompt.md`) that ranks and writes proposals. The matrix is the contract; the prompt can change freely. |
| Location | `openframe-oss-lib/openframe-test-service-core/test-coverage-analyser/` (user's choice), next to the library it measures. Inside the Java release path filter — results gitignored. |
| Delivery | `results/<date>/report.md` for humans; no push, no Slack in milestone 0. |
| No code changes | Milestone 0 proposes; it does not scaffold tests. |
| Plan | `coverage-plan.toml`, items at feature-area granularity keyed by matrix ops. Status is human-owned; `done` is proved by the matrix (direct tests), effort is computed from missing fixtures, and the headless run may only append `proposed` items. TOML because Python 3.11+ parses it from the stdlib and it takes comments. |
| Known gaps | Applied by the extractor from the `**Ops:**` selectors of each entry (keys, unique op names, controller classes, path patterns); prose never selects. The report inherits the result instead of re-deriving it. |
| History | `history.jsonl`, one line per run date, committed with the plan; deltas in the Plan section. |

## Facts the design relies on (verified 2026-09-12)

- **Schemas:** 41 `*.graphqls` files (23 oss-lib, 16 saas-tenant, 2 saas-lib, 0 saas-shared); 92 query
  and 133 mutation names in `src/main`; no `Subscription`. Ticket operations live in
  `openframe-saas-ai-agent` and are served on `/chat/graphql`; the rest on `/api/graphql`.
- **Controllers:** 65 `@RestController`/`@Controller` classes, 212 handler methods; catch-all proxies in
  `IntegrationController` (gateway and external-api). No OpenAPI document is committed; the external
  API's spec is generated by springdoc at `/api-docs`.
- **Gateway prefixes** (`configs/base/openframe-saas-gateway.yml`): tenant `/api/**`, `/chat/**`,
  `/clients/**`, `/external-api/**` all `StripPrefix=1`; shared `/sas/**` to the auth server (context
  path), `/api/**` strip 1; `/oauth/**` is the BFF on the gateway itself.
- **Dashboard app:** `flamingo-stack/openframe-oss-frontend` (public), Next.js 16 + Relay,
  `schema.graphql` committed (69 query / 83 mutation fields — a merged subset of the product plus
  test-clock fields), 84 routes under `src/app/(app)/`, REST through `src/lib/api-client.ts`
  (`apiClient.<method>('/api/…')`), tickets/chat via raw `` `#graphql `` strings to `/chat/graphql`.
  The deployed image tag (1.0.92 tenant qa, 1.0.97 shared qa) has no commit anchor; the committed
  `openframe-frontend-core` version is frozen at 0.0.108 while npm is at 0.0.61x.
- **Test library:** 212 `@Test` methods in 37 classes (7 disabled, 5 with assumptions); 58 GraphQL
  text-block documents (50 distinct root fields); ~81 REST method+path pairs; static client classes
  under `api/`, fluent login chain in `api/auth/AuthFlow.login`. No feature/ticket annotations — tags
  and display names are the only metadata.
- **Nightly phases** (`configs/base/openframe-saas-test.yml`): `functional` runs everything not
  tagged registration/registration-negative/org-create/device/scheduled/archive/org-archive/
  admin-setup/admin-teardown/ai/external-api; each excluded tag has its own phase.
- **CI:** `openframe-test-service-core/**` is in the `java` filter of `changes.yaml`; a push to `main`
  touching it publishes a new library version.
- **macOS toolchain quirks hit while building:** bash 3.2 (`"${arr[@]}"` on an empty array fails
  under `set -u`), `git grep -E` without `\b`, `git log -G` needs `--extended-regexp` and
  `[[:space:]]`.

## Milestone 0.5 — plan layer (implemented 2026-09-13)

`coverage-plan.toml` + `history.jsonl` + the Plan section of `coverage.md` + prompt Step 3b. Seeded

## Milestone 1 — scaffold the top proposals on a branch

Same shape as the nightly analyser's fix step: `run-local.sh --scaffold` creates a worktree
`test/coverage-<date>` from `origin/main` under `<flamingo root>/worktrees/`, and the prompt gains a
step that, for each P1 proposal, adds the `Queries` constant, the client method, the DTOs (fields
from the schema at the SHA) and the test class or method, one commit per proposal, compiled with
`mvn -q -o -pl openframe-test-service-core -am compile -DskipTests`. Never pushes unless `--push`;
draft PR body = `report.md`. Guard: proposals touching destructive or rate-limited surface are
scaffolded as `@Disabled` with the reason in the display name.

## Milestone 2 — depth, not just presence

Per covered operation: count `direct` tests, whether any carries a negative tag (`negative`,
`reject`, `injection`) or asserts an error path (`userErrors`, `statusCode(4..)`), and whether the
test asserts the response body beyond non-null. Add a `depth` column (`smoke` / `asserted` /
`negative`) and let the report rank thin coverage on UI-critical mutations above brand-new queries.

## Milestone 3 — recurring run and trend

- Weekly `Workflow`/cron in the qa cluster or a GitHub Action in `openframe-oss-lib` (matrix only —
  no secrets needed beyond a token for the private repos if any): commit `coverage.md` to a
  dedicated branch or publish it as a build artefact, never to `main` (release trigger).
- Keep `results/<date>/coverage.json` history to chart covered %, gap-ui count and "introduced and
  uncovered" over time; flag any run where gap-ui grows.
- Slack: post the summary section of `report.md` to the QA channel using the same bot token the
  nightly uses (`SLACK_OAUTH_TOKEN` in the `openframe-saas-test` secret).

## Risks and notes

- The UI at `origin/main` may be ahead of what qa runs; a gap on an operation only main uses is real
  for the next release, not for today's qa. The report says "the app's main branch uses it".
- Name-based instance-call attribution can over-credit when two client classes share a method name
  and are referenced in the same body; today only the auth flows share names (`discoverTenant`,
  `startFlow`) and both are login paths, so the effect is nil. Re-check if `api/` grows another
  fluent class.
- The extractor does not execute anything; a `covered` operation whose test is skipped at runtime by
  an assumption still counts. `assumes: true` is reported for that reason.
- The first known-gaps entries were drafted from the survey, not agreed with anyone. Until confirmed
  they are marked *proposed*, and the report applies them anyway — read that section with care.
