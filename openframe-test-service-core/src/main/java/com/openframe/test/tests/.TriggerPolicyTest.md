`TriggerPolicyTest.java` drives a full policy re-evaluation from the outside: it refetches every host a policy targets, forces the aggregation cron, and asserts the policy comes back compliant.

**Replaces both UI cases in `MonitoringTest`** (`testWindowsVersionPolicyStatus`, `testEmptyPolicyStatus`), which asserted the "Compliant" badge on the Monitoring page without ever producing that state — they failed repeatedly in the scheduled pipeline with `"Pending"` or `""` whenever the run landed before an hourly aggregation. `MonitoringTest` had no cases left and was removed; `MonitoringPage` stays as a reusable page object.

## Key Components

| Method | Description |
|---|---|
| `testWindowsVersionPolicyIsCompliant()` | The targeted policy: asserts `failing_host_count == 0` and `passing_host_count == assigned hosts` |
| `testEmptyPolicyIsCompliant()` | The untargeted policy: asserts no assigned hosts and both counts `0` |
| `reEvaluate(policy, hosts)` | Shared flow — refetch each assigned host, wait for it to report, trigger `cleanups_then_aggregation`, wait for `host_count_updated_at` to advance |
| `resolveSeededPolicy(name, expectedQuery)` | Resolves by name and guards the query against drift |

## Sequence

1. `MonitoringApi.getPolicies()` → find the policy by name
2. `MonitoringApi.getPolicy(id)` → the detail read, which is where `hosts_include_any` comes from
3. Guard the query against drift, then for each assigned host: record `policy_updated_at`, `refetchFleetHost(fleetId)`, wait for it to advance (a no-op for `Empty`, which targets nothing)
4. `triggerCronSchedule(CLEANUPS_THEN_AGGREGATION)`
5. Poll the policy until `host_count_updated_at` passes the pre-run baseline
6. Assert compliance on the now-known-fresh counts — the API equivalent of the "Compliant" badge

## Why `host_count_updated_at`, not `updated_at`

A policy's `updated_at` tracks edits to the policy *record* — neither a host refetch nor the aggregation cron touches it. On a freshly seeded policy `updated_at` equals `created_at` and stays there while aggregation runs repeatedly. Fleet stamps `host_count_updated_at` when it recomputes `passing_host_count` / `failing_host_count`, so that is the field that moves.

## Why it waits for host results before aggregating

The aggregation stamps `host_count_updated_at` whenever it runs, regardless of whether any host reported something new. Without the host-level wait in step 3, the test would still pass with the refetch removed — the wait is what makes the assertion mean "a fresh evaluation was rolled up".

## The two policies differ in what "compliant" means

`Windows version` targets one host, so compliant is `failing == 0` **and** `passing == assigned hosts`. `Empty` ("Policy without devices") is deliberately untargeted: Fleet returns a **null** `hosts_include_any`, no host evaluates it — verified against qa, where it is absent from every host's policies list — yet aggregation still stamps its counts. Compliant there means both counts are `0`.

## Query drift

Editing a policy's query silently resets its pass/fail results, which surfaces later as an unexplained "not compliant" plus a null `host_count_updated_at`. `resolveSeededPolicy` compares the live query against `MonitoringGenerator` and fails with both queries named, rather than letting it show up downstream.

## Preconditions

- The policy named by `POLICY_NAME` must exist with at least one assigned host (`CreatePolicyTest` seeds it and assigns the host).
- Those hosts must be ONLINE so they check in and apply the refetch.
- `cleanups_then_aggregation` is **server-wide** — it runs the cron for the whole Fleet instance, so on a shared Fleet this affects every tenant.

## Running

```bash
mvn test -Pai-test -Dtest=TriggerPolicyTest
```
