`FleetWait.java` polls a Fleet read until a condition holds. It is the shared wait used by the tests that trigger Fleet work asynchronously.

## Key Components

| Method | Description |
|---|---|
| `until(what, read, satisfied)` | Polls `read` every 3s until `satisfied` holds, up to `DEFAULT_TIMEOUT_SECONDS` (180) |
| `until(what, read, satisfied, timeoutSeconds)` | Same with an explicit deadline |

Returns the last value successfully read — whether or not it satisfied the condition — so the caller can assert on it and produce a domain-specific failure message rather than a generic timeout.

## Why polling at all

Fleet's triggers are asynchronous. A host refetch only raises a flag that the host applies on its next check-in, and policy pass/fail aggregates are recomputed by a cron. Neither has landed by the time the POST returns.

## Why a failed poll does not end the wait

An isolated non-200 from the Fleet proxy between two healthy polls has been observed on qa. `RetryingHttpClientFactory` does not cover it — it retries connection establishment, not error statuses. Without this tolerance, one blip anywhere in a 180s wait fails an otherwise good run. A failed read (or a predicate that throws on a partial response) is logged at WARN and counted as "not yet"; only a wait that never got a readable response fails.

## Usage

```java
FleetHost after = FleetWait.until(
        "policies to be re-evaluated on Fleet host " + fleetId,
        () -> DeviceApi.getFleetInfo(fleetId),
        h -> Instant.parse(h.getPolicyUpdatedAt()).isAfter(baseline));
```

Callers: `TriggerPolicyTest`.
