An in-memory, rolling-window rate limiter for Debezium connector recreations. It enforces a configurable maximum number of recreations per connector per hour using JVM-local state, serving as a lightweight alternative to `MongoRecreationTracker` in single-tenant pod deployments.

## Key Components

| Member | Description |
|---|---|
| `WINDOW` | Fixed 1-hour rolling window for recreation event tracking |
| `maxPerHour` | Configurable cap via `openframe.debezium.recovery.max-recreations-per-hour` (default: `1`) |
| `eventsByBase` | `ConcurrentHashMap` keyed by connector base name, holding a deque of `Instant` timestamps |
| `canRecreate(baseName)` | Checks whether the connector is under its hourly recreation limit; logs a warning if the cap is reached |
| `record(baseName)` | Appends the current timestamp to the connector's event deque |
| `prunedQueue(baseName)` | Internal helper that evicts expired entries (older than 1 hour) on read, bounding memory without a background sweep |

**Activation:** Enabled when `openframe.debezium.recovery.recreation.in-memory=true`. Declared `@Primary`, so it takes precedence over `MongoRecreationTracker` when both beans are candidates.

## Usage Example

```java
// application.yml
// openframe.debezium.recovery.recreation.in-memory: true
// openframe.debezium.recovery.max-recreations-per-hour: 3

@Autowired
RecreationTracker tracker;

String connector = "orders-connector";

if (tracker.canRecreate(connector)) {
    tracker.record(connector);
    // proceed with connector recreation
} else {
    log.warn("Skipping recreation — hourly limit reached for {}", connector);
}
```

> **Trade-off:** State is JVM-local and resets on pod restart. Under multi-replica deployments without `@SchedulerLock`, the cap may be slightly exceeded across replicas — by design, acceptable for runaway-protection use cases.
