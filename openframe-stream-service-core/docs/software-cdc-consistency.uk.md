# CDC-проєкція софту: дизайн консистентності

Довідник по пайплайну Fleet `host_software` → read model у Mongo (інвентар софту й вразливості).
Описує, що гарантує поточний код, як саме, і де лишаються ризики.
Спирається на код `main` (листопад 2026) разом із кроками 1–2 розділу 7.1; номери рядків орієнтовні.

Статус: **живий довідник, відновлений з коду.** Попередній дизайн, що існував усно та в нотатках
(автор — А. Яковенко), у хабі відсутній, а сам автор пішов з команди. Тож джерело правди — цей документ,
і його треба редагувати на місці, коли пайплайн змінюється.

## 1. Обсяг і пайплайн

Fleet — система запису для встановленого софту і привʼязаних до нього CVE. UI потрібні списки на рівні
всього тенанта з сортуванням і пагінацією (софт, вразливості, перегляди по пристрою), а API Fleet не може
ефективно віддавати їх у великому масштабі. Тому ми тримаємо денормалізовані read model у Mongo і
наповнюємо їх із Fleet через CDC.

```
Fleet MySQL                Debezium → Kafka            openframe-stream-service
  host_software  ──CDC──▶  події зміни рядків  ──────▶  DeviceSoftwareHandler
                                                              │  (подія = лише тригер)
                                                              │  перечитує ПОТОЧНИЙ
                                                              │  софт хоста з Fleet API
                                                              ▼
                                                   device_software  (Mongo, копія-джерело правди)
                                                              │
                                              ┌───────────────┴───────────────┐
                                              ▼                               ▼
                                     SoftwareProjector              VulnerabilityProjector
                                              ▼                               ▼
                                     software (read model)          vulnerabilities (read model)
                                              └───────────────┬───────────────┘
                                                              ▼
                                         API (за прапорцем openframe.features.software-read-model.enabled)
```

Прапорці:
- `openframe.fleet.software-cdc.enabled` вмикає обробник у stream (`DeviceSoftwareHandler`).
- `openframe.features.software-read-model.enabled` перемикає шлях читання в API з Fleet на
  read model (`SoftwareInventoryService`, `VulnerabilityInventoryService`).

Обидва вимкнені, доки Debezium не захоплює `host_software` і моделі не заповнені початковими даними (backfill).

## 2. Колекції, ключі, індекси

### `device_software` — похідне джерело правди (один рядок на пристрій × тайтл софту)
`DeviceSoftware.java`
- унікальний `tenant_machine_title {tenantId, machineId, softwareTitleId}` — природний ключ; через нього
  проходить кожен upsert і кожне читання окремого рядка.
- `tenant_machine {tenantId, machineId}` — читання «всі тайтли на цьому хості» під час reconcile.
- `tenant_title_connected {tenantId, softwareTitleId, machineConnected, machineId}` — «підключені пристрої з цим тайтлом»
  для агрегації проєктора софту (`machineId` — під її сортування); провідні ключі обслуговують і запити
  без `machineConnected`.
- `tenant_vuln_connected {tenantId, vulnerabilities, machineConnected, machineId}` — multikey; «підключені пристрої з цим CVE»
  для агрегації проєктора вразливостей.

Поля, що приходять із Fleet: `name`, `versions[]`, `vulnerabilities[]` (id CVE), `source`, `updatedAt`.

### `software` — read model (один рядок на тенант × тайтл софту)
`Software.java` · унікальний `tenant_title {tenantId, softwareTitleId}`, а також
`tenant_name {tenantId, nameLower}`, **`tenant_devices {tenantId, devicesCount:-1}`**,
`tenant_cveCount {tenantId, cveCount:-1}`, `installations_machine {tenantId, installations.machineId}`.
Зберігається денормалізовано: `devicesCount`, `cveCount`, `latestVersion`, `installations[]`.

### `vulnerabilities` — read model (один рядок на тенант × CVE)
`Vulnerability.java` · унікальний `tenant_cve {tenantId, cveId}`, а також
**`tenant_devices {tenantId, devicesCount:-1}`**, `tenant_discovered {tenantId, discoveredAt:-1}`,
`tenant_title {tenantId, affectedSoftware.softwareTitleId}`.
Зберігається денормалізовано: `devicesCount`, `affectedSoftware[]` (кожен елемент зі своїм `devicesCount`).
Колишній список `machineIds[]` прибрано в #2956: уражені пристрої обчислюються під час читання
з `device_software`, денормалізованим лишається тільки число `devicesCount`.

## 3. Ключовий принцип: подія як тригер + перерахунок із джерела

`DeviceSoftwareHandler.handle` (`DeviceSoftwareHandler.java:52`) свідомо бере з payload Debezium
**лише одне**: `host_id` (з `before` при видаленні, з `after` в інших випадках, рядок 58).
Значення колонок рядка він **не** застосовує. Далі він:

1. Визначає хост → тенант/машину (`FleetHostResolver`) і пропускає хости, які не вдалося визначити (рядок 67).
2. Перечитує **весь поточний** список софту хоста з Fleet API
   (`FleetHostSoftwareCache.hostSoftware`, рядок 88). Джерело правди — Fleet.
3. Узгоджує `device_software` для цього хоста (`reconcile`, рядок 87): upsert кожного наявного тайтлу,
   видалення кожного рядка, якого більше немає (рядки 102–130).
4. Передає `SoftwareProjectionTrigger` тайтли й CVE, яких це торкнулося (`titlesChanged`, `cvesChanged`),
   і той перераховує read model рівно для них. Через ту саму точку входу проходять `DeletedMachineCleanup`
   і `DeviceSoftwareConnectivitySync`; вона ж пише метрики `openframe.software.projection`.

Обидва проєктори **рахують з нуля**, ніколи не дельтою, і рахують усередині Mongo
(`DeviceSoftwareAggregationRepository`), не завантажуючи рядки в памʼять:
- `SoftwareProjector.project` бере `rollUpTitle`: одна агрегація по підключених рядках тайтла дає
  `devicesCount` (рядок унікальний на машину × тайтл, тож distinct не потрібен), `cveCount`, обʼєднання версій
  і ключів Windows-програми. `latestVersion` обирає Java через `SoftwareVersions::compare` (порівняння по
  числових сегментах) з невеликої множини версій. Поки `installations[]` лишається в `Software` (крок 4
  розділу 7.1), агрегація повертає і його. Немає рядків → рядок read model видаляється.
- `VulnerabilityProjector.project` бере `rollUpCve`: агрегація по підключених рядках із цим CVE групує за тайтлом
  і рахує `devicesCount` як **distinct** машин — одна машина може мати CVE через два тайтли.
  Немає рядків → видалення.

### Чому саме так
Це робить увесь пайплайн **ідемпотентним** і **самовідновним**: оскільки кожна подія відкидає
payload і заново виводить стан хоста з Fleet, дубльована, переставлена чи повторно програна подія
дає той самий результат, що й одноразова обробка. Це свідома відповідь на доставку Kafka
at-least-once: коректність не залежить від того, чи кожну подію побачено рівно один раз і в правильному порядку.

## 4. Які властивості консистентності реально дає код

| Властивість | Як | Де |
|---|---|---|
| **Ідемпотентність при at-least-once** | подія не несе стану; хост повністю перевиводиться з Fleet | `DeviceSoftwareHandler.java:58,88` |
| **Самовідновлення** | будь-яка подія для хоста перебудовує всю його множину `device_software` | `reconcile`, рядки 102–130 |
| **Дедуплікація читання в межах одного коміту Fleet** | кеш з ключем `tenant:host:commitTs`; пачка подій рядків з одного коміту звертається до Fleet один раз | `FleetHostSoftwareCache.java:34-35`, `DeviceSoftwareHandler.java:78-85` |
| **Немає застарілого списку між комітами** | `commitTs` пізнішого коміту — новий ключ кешу, тож він ніколи не віддасть список, прочитаний для ранішого коміту | там само |
| **Лічильники проіндексовані для UI** | `devicesCount` зберігається і має індекс (`tenant_devices`), тож сортування, фільтр і пагінація виконуються в Mongo, а не в памʼяті | `Software.java`, `Vulnerability.java` |

## 5. Сім пунктів Кирила: заява проти коду

1. **Лічильник денормалізовано для сортування** — ✅ `devicesCount` зберігається + `tenant_devices {…, devicesCount:-1}` в обох read model.
2. **Дві колекції (пристрої / вразливості)** — ✅ `device_software` (правда) наповнює `software` і `vulnerabilities`.
3. **Архівований пристрій не входить у лічильник** — ✅ **закрито** (раніше була прогалина). Видалення
   пристрою тепер прибирає його рядки `device_software` і перепроєктує зачеплені тайтли/CVE, тож лічильники
   зменшуються на цей пристрій. Див. G3.
4. **Ідеальна консистентність при Kafka at-least-once** — ✅ досягнуто, але через **ідемпотентний
   перерахунок із джерела**, а не через трюк із лічильником. Дублі, повтори й перестановки сходяться.
5. **Гонки розвʼязано через версію** — ❌ **немає ні `@Version`, ні оптимістичного блокування, ні транзакції.**
   Безпека тримається на перерахунку і ключі читання `commitTs`, який упорядковує *читання*, а не *запис*. Див. G1.
6. **Великі дані → пакети** — ❌ **пакетної обробки немає.** `reconcile` робить `find`+`save` на кожен тайтл
   у циклі; кожен зачеплений CVE запускає проєктор, що перезавантажує всю когорту пристроїв. Див. G2, G4.
7. **Найефективніший лічильник / уникати перерахунку** — ⚠️ код робить **навпаки**: завжди
   перераховує. Це виправдано пунктом 4, але ціна реальна і зосереджена в проєкторі CVE (G2).

(У ранішому списку Кирила був 8-й пункт — «усі підходи до консистентності з дизайну Яковенка», — який
він прибрав під час редагування; того дизайну в хабі немає, автор пішов, і цей документ заміняє
його як довідник. Див. заголовок.)

Пункти **4 і 7 прямо суперечать один одному**, і код розвʼязує це на користь 4 (коректності).
Чесне формулювання для команди: ми обрали *завжди коректно, перерахунок на кожну подію* замість
*дешевих, але крихких дельта-лічильників*. Дельта-інкременти рахували б двічі при повторній доставці at-least-once.

## 6. Відомі прогалини й ризики

### G1 — Гонки запису на тому самому хості (немає версії, немає транзакції)
`reconcile` — це послідовність read-modify-write з незалежних операцій Mongo (`find existing` → N× `save` →
M× `delete`), без транзакції й без оптимістичної версії. Якщо дві події для **того самого хоста**
обробляються паралельно (можливо, якщо споживач не серіалізує обробку по хосту — **перевірити партиціювання**),
вони можуть переплестися: обидві прочитають стару множину, обидві зроблять upsert, і «видалення відсутніх»
однієї може прибрати рядок, який щойно записала інша, або залишити осиротілий. Кеш за `commitTs` лише
дедуплікує читання з Fleet; запису він не серіалізує.
Наслідок: тимчасово неправильний `devicesCount` або зайвий/відсутній рядок `device_software`, доки
наступна подія для цього хоста його не виправить.
**Перевірено 2026-11-09:** сьогодні stream обробляє події послідовно (1 репліка × 1 потік), тож G1 не
трапляється. Але ключ партиції — `(host_id, software_id)`, а не `host_id`, тож G1 стане реальною з
підняттям concurrency чи реплік. Деталі — розділ 7.1, «Чи буде `devicesCount` консистентним».
Варіанти: (a) серіалізувати обробку по `host_id` (партиціювати топік Debezium за хостом або тримати
блокування/чергу на хост у споживачі); (b) додати `@Version` у `device_software` і повторювати при конфлікті;
(c) прийняти як є, бо наступна подія для хоста все вирівнює, — і задокументувати вікно eventual consistency.

### G2 — Розгалуження в проєкторі CVE (справжня проблема масштабу)
**Стан:** кроки 1–2 розділу 7.1 зроблено: рядки більше не вантажаться в памʼять. Перерахунок на кожну
подію лишається (до кроку 5), а масив `installations[]` ще переписується (до кроку 4). Опис нижче — стан до кроку 2.

`VulnerabilityProjector.project` викликає `findByTenantIdAndVulnerabilitiesContaining(tenant, cve)` —
**кожен** пристрій, що має цей CVE, — на **кожну** подію хоста, яка цього CVE торкається. Для CVE, наявного
на N пристроях, зміна одного хоста коштує O(N) перезавантаження й перерахунку. Популярний CVE (наприклад,
libc/openssl на тисячах кінцевих точок) означає, що кожна окрема подія хоста перечитує тисячі рядків.
**Проєктор софту має ту саму проблему.** Який тайтл перераховувати, визначає список тайтлів хоста, але
`SoftwareProjector.project` вантажить усі рядки тайтла по всьому тенанту
(`findByTenantIdAndSoftwareTitleIdAndMachineConnectedTrue`) і переписує весь масив `installations[]`.
Оновлення Chrome на N машинах — це N подій × N рядків, тобто O(N²) читань і N записів масиву на N елементів.
Вибраний шлях — розділ 7.1. Варіанти, які розглядали: (a) debounce/обʼєднання по `(tenant, cve)` у короткому вікні з одним перерахунком;
(b) винести проєкцію з потоку обробника в асинхронний воркер з ключем `(tenant, cve)` і згортанням;
(c) інкрементне ведення `devicesCount` для CVE під захистом версії (втрачається частина простоти
перерахунку — зважити з G1 / пунктом 4);
(d) спочатку обмежити/виміряти очікувані розміри когорт (див. «Відкриті питання»).

### G3 — Архівовані / виведені пристрої завищують лічильники — ✅ ЗАКРИТО
**Проблема (була):** лічильник — це `distinct(machineId)` по `device_software`. Пристрій випадає
лише тоді, коли подія Fleet `host_software` для нього запускає reconcile, який бачить, що його немає.
Видалений чи виведений з обслуговування пристрій перестає генерувати події Fleet, тож його рядки
`device_software` лишалися б і далі завищували кожен `devicesCount`, у який вони входять, — найімовірніший
у продакшені баг «лічильник завеликий».

**Виправлення (варіант a):** сигналом є видалення пристрою. Обидва шляхи виведення — `DeviceService`
(статус → `DELETED`) і `AgentUninstallService` (видалення агента) — уже викликають
`DeletedMachineCleanup`; цей компонент тепер, окрім очищення розкладів, видаляє рядки пристрою
в `device_software` (`deleteByTenantIdAndMachineId`) і перепроєктує кожен тайтл софту й CVE,
яких пристрій торкався, тож денормалізовані лічильники зменшуються рівно на цей пристрій (тайтл/CVE,
що існував лише на ньому, видаляється з read model). Щоб це було досяжно з сервісів, які виконують видалення,
обидва проєктори переїхали з `openframe-stream-service-core` в `openframe-data-mongo-sync`
(`com.openframe.data.service.rmm.software`) — це їхнє природне місце, бо вони залежать лише від
репозиторіїв.
Див. `DeletedMachineCleanup.cleanUpDeletedMachine` / `removeFromSoftwareReadModel`.

**Ще відкрито:** `DeviceStatus.ARCHIVED` сьогодні ніколи не встановлюється для машини (кожне виведення
використовує `DELETED`), тож окремого шляху архівації, до якого можна підʼєднатися, немає. Якщо такий
колись зʼявиться, він має викликати те саме очищення. Хост, що назавжди замовк, але *не* видалений, — це досі G6.

### G4 — Немає пакетної обробки / N+1 записів
`reconcile` робить один `find` + один `save` на кожен тайтл і один `delete` на кожен прибраний тайтл;
кожен проєктор робить свої `find` + `save`. Для хоста із сотнями тайтлів це сотні запитів туди-назад.
`BulkOperations` (масовий upsert, масове видалення) суттєво це скоротили б. Ризик для коректності низький,
але реальна ціна в затримці й пропускній здатності на масштабі.

### G5 — Час події проти реального часу
`discoveredAt` і `updatedAt` встановлюються через `Instant.now()` у момент обробки
(`VulnerabilityProjector.java:54,56`, `SoftwareProjector.java:59`), а не з часу коміту Fleet/CDC.
Повтори чи backfill проставлять «зараз», тож ці поля — мітки обробки, а не часові мітки джерела.
Сьогодні це прийнятно; варто памʼятати про це, перш ніж хтось сортуватиме/фільтруватиме за `discoveredAt`,
ніби це справжній час виявлення.

### G6 — Міжхостові лічильники припускають, що кожен хост актуальний
Лічильник на рівні тенанта коректний настільки, наскільки коректне обʼєднання `device_software` усіх його
хостів. Хост, що назавжди замовк (агент упав, реєстрацію втрачено) без події видалення (див. G3),
безстроково спотворює кожен лічильник, до якого він входить.

   Без інкрементних дельт, щоб ідемпотентність із пункту 4 вціліла.
4. **Пакетна обробка G4** — механічний виграш, щойно розібралися з попереднім.

## 7.1. План переходу для G2

### Цільова схема

```
reconcile(host) ──► device_software (upsert/delete)
        │
        └──► dirty{tenantId, kind, key}  (upsert: 1000 подій по Chrome = 1 рядок)
                         │
                         ▼  flusher: @Scheduled + @SchedulerLock, раз на flush-interval
              перерахунок із device_software засобами Mongo (count / aggregation)
                         │
            ┌────────────┴─────────────┐
            ▼                          ▼
   software (тонкий):            vulnerabilities:
   метадані, latestVersion,      devicesCount, affectedSoftware[]
   devicesCount, cveCount        (масив на тайтли, не на машини)
   — без installations[]

читання: списки  → software / vulnerabilities (сортування за індексом tenant_devices)
         деталі  → device_software напряму (пристрої тайтла, софт і CVE пристрою)
```

Що лишається як є: подія — лише тригер, стан хоста перечитується з Fleet, read model завжди
перераховується з `device_software`, а не дельтами (пункт 4, розділ 3).

Схема вище — кінцевий стан. Згортання (`dirty` + flusher) вмикаємо за умовою з кроку 5; до того проєктори
викликаються одразу, але вже через єдину точку входу з кроку 1.

### Розміри тенантів (2026-11-09)

Пʼять найбільших тенантів за активними девайсами: **242, 231, 214, 141, 107**. Для оновлення Chrome у
найбільшому тенанті це:

| | зараз | після кроків 2–4 | + згортання (крок 5) |
|---|---|---|---|
| софт за весь rollout | 242 × 242 ≈ 58 тис. рядків у памʼять + 242 перезаписи масиву на 242 елементи | ≈ 58 тис. записів індексу всередині Mongo, запис — кілька полів | кілька перерахунків |
| CVE (подія чіпає ~50 CVE) | ≈ 3 млн рядків у памʼять | ≈ 3 млн записів індексу в Mongo, без передачі даних | на порядки менше |

Робота росте як N². На N ≈ 250 основну ціну (рядки в памʼяті й переписування масиву) прибирають кроки 2–4,
а згортання майже нічого не додає. При N ≈ 2 000 це вже ~4 млн записів індексу на тайтл за rollout
і сотні мільйонів з боку CVE. Тоді без згортання stream відставатиме на масових оновленнях.

### Кроки (кожен — окремий PR в oss-lib, поки обидва прапорці на stage/prod вимкнені)

**Крок 1. Єдина точка входу й метрики (поведінка не змінюється).** ✅ Зроблено.
- `SoftwareProjectionTrigger` з `titlesChanged(tenantId, titleIds)` і `cvesChanged(tenantId, cveIds)`.
  Її викликають `DeviceSoftwareHandler.reconcile`, `DeletedMachineCleanup` і
  `DeviceSoftwareConnectivitySync` замість прямих викликів проєкторів. Поки що реалізація викликає
  проєктори одразу; згортання з кроку 5 замінить лише її.
- Micrometer-таймер на перерахунок з тегом `kind = title | cve` і розподіл кількості рядків на перерахунок.
  Назва з префіксом `openframe.`, інакше метрику відкине allowlist Alloy (`openframe_.*`).

**Крок 2. Перерахунок засобами Mongo, без завантаження рядків у памʼять.** ✅ Зроблено.
- `SoftwareProjector`: одна агрегація на тайтл — `$match {tenantId, softwareTitleId, machineConnected: true}`
  → `$group` з `count` (рядок унікальний на машину×тайтл, тож distinct не потрібен), `$addToSet` версій,
  `installerTypes` і CVE (після `$unwind`), `$first` для зразка полів назви/програми. Результат —
  один маленький документ; `latestVersion` і далі обирає Java (`SoftwareVersions::compare`)
  з невеликої множини версій.
- `VulnerabilityProjector`: агрегація `$match {tenantId, vulnerabilities: cve, machineConnected: true}` →
  `$group` за тайтлом (`$addToSet machineId` для `devicesCount` тайтлу) і окремо `$group` за `machineId`
  для загального `devicesCount`. **Distinct тут обовʼязковий:** одна машина може мати той самий CVE
  через два тайтли, і плаский `countDocuments` порахує її двічі.
- Індекси: `{tenantId, softwareTitleId, machineConnected}` замість `tenant_title` (покриває і count,
  і деталі); `{tenantId, vulnerabilities, machineConnected}` замість `tenant_vuln`.

**Крок 3. Перевести читання деталей на `device_software`** (за вимкненим прапорцем
`openframe.features.software-read-model.enabled`, тож ризику немає):
- `DeviceSoftwareReadModelQuery` (софт пристрою): `device_software` за `{tenantId, machineId}` +
  метадані з `software` за списком `softwareTitleId`;
- `TenantSoftwareReadModelQuery` (пристрої тайтла, два місця): `device_software` за
  `{tenantId, softwareTitleId, machineConnected: true}` з пагінацією в Mongo;
- `DeviceVulnerabilityReadModelQuery` (CVE пристрою): `device_software` за `{tenantId, machineId}`,
  розгорнути `vulnerabilities`.

**Крок 4. Прибрати `installations[]` з `Software`** і індекс `installations_machine`.
Міграція даних не потрібна: `save` переписує документ цілком, тож старе поле зникне при наступному
перерахунку або backfill. Видалення індексу — ручна команда для бази, виконує людина.

**Крок 5. Згортання (debounce) — за умовою.** Робимо, коли виконується хоч одна з умов:
- найбільший тенант наближається до ~1 000 активних девайсів;
- метрика з кроку 1 показує ріст часу перерахунку або лаг споживача на масових оновленнях;
- **обовʼязково до** підняття `spring.saas.kafka.listener.concurrency` чи кількості реплік stream
  (розділ «Чи буде `devicesCount` консистентним»).

Як:
- Нова колекція `software_projection_dirty`: `{tenantId, kind: TITLE | CVE, key, dirtyAt}`,
  унікальний індекс `{tenantId, kind, key}`. Реалізація `SoftwareProjectionTrigger` робить upsert
  позначок замість виклику проєкторів.
- Порядок у `reconcile`: позначка **до** запису в `device_software` і **після** нього (два дешевих
  ідемпотентних upsert). Позначка «до» переживе падіння між записом і позначкою: при повторній доставці
  дифф порожній і нових позначок не буде. Позначка «після» не дає flusher перерахувати тайтл між
  позначкою і записом та зняти її зі старим станом.
- Flusher у stream (за тим самим прапорцем `openframe.fleet.software-cdc.enabled`): `@Scheduled` +
  `@SchedulerLock`, бере пачку позначок, для кожної: прочитати `dirtyAt` → видалити позначку з умовою
  `dirtyAt == прочитаний` → перерахувати з джерела. Якщо подія знову позначила ключ, видалення не
  спрацює або позначка зʼявиться заново, і ключ перерахує наступне вікно.
- Конфіг без дефолтів, значення лише в `configs/dev/openframe-saas-stream.yml` (saas-shared):
  `flush-interval`, `batch-size`, `lock-at-most-for`.
- Ефект: оновлення Chrome на 1000 машинах — 1000 записів у `device_software` (вони неминучі) і один
  перерахунок Chrome на вікно, а не 1000. Вартість падає з N×N до (кількість вікон)×N.
- Поки writer вимкнений, позначки від видалень пристроїв в api накопичуються. Їх не більше, ніж тайтлів і CVE
  тенанта, і flusher розбере їх після вмикання.

**Крок 6. Страхувальна мережа.** Періодичний прохід (наприклад, раз на добу, інтервал з конфігу), що
перераховує всі тайтли й CVE тенанта (після кроку 5 — ставить їм позначки). Він вирівнює все, що могло
розійтися (G1, втрачена позначка, гонка з api, ручне втручання в базу).

**Крок 7 (необовʼязковий). G4** — `BulkOperations` у `reconcile`.

### Чи буде `devicesCount` консистентним

Не миттєво, а **eventually consistent з обмеженим вікном**. Тут два різні рівні:

| Рівень | Гарантія | Що може зламати | Чим закрито |
|---|---|---|---|
| `devicesCount` ↔ `device_software` | дорівнює кількості рядків на момент останнього перерахунку; після кроку 5 відставання — одне вікно flush | втрачена позначка; два перерахунки того самого тайтла одночасно (stream і api) | щоденний прохід (крок 6); після кроку 5 — подвійна позначка й один flusher під `@SchedulerLock` |
| `device_software` ↔ Fleet | сходиться з наступною подією хоста | G1 (паралельні події одного хоста), G6 (хост замовк без видалення), збій читання з Fleet, хости без backfill | G1 — розділ 6; G6 і backfill — відкриті, не залежать від цього плану |

**Що сьогодні реально відбувається з паралельністю** (перевірено 2026-11-09 на `origin/main` saas-shared):
- `SharedFleetKafkaListener` слухає всі чотири Fleet-топіки через `saasTenantKafkaListenerContainerFactory`.
  `spring.saas.kafka.listener.concurrency` не задано в жодному середовищі, тож це один потік споживача.
- Deployment `openframe-saas-stream` має `replicas: 1` без HPA; обробка в обробнику синхронна.
- Отже сьогодні stream обробляє всі події Fleet строго послідовно: ні G1, ні паралельних перерахунків
  того самого тайтла з боку stream немає.

Але це випадковість конфігурації, а не гарантія:
- Топіки мають 3 партиції, а ключ повідомлення Debezium — первинний ключ рядка `host_software`,
  `(host_id, software_id)`, а не `host_id`. Події одного хоста розходяться по різних партиціях.
  Варто підняти concurrency або кількість реплік stream — і G1 та гонка перерахунку стають реальними.
- Паралельний запис можливий уже сьогодні з інших сервісів. `DeletedMachineCleanup` і
  `DeviceSoftwareConnectivitySync` викликаються з api-lib (api, external-api, client) і перераховують
  ті самі `software` / `vulnerabilities`, поки stream робить те саме. `save` — «хто останній, той і правий»,
  тож при збігу в часі лічильник може лишитися неправильним до наступної події по тайтлу. Це рідко
  (лише видалення й архівація), але реально; закриває щоденний прохід (крок 6).

Після кроку 5 `software` / `vulnerabilities` пише лише flusher, і перерахунок завжди йде після останньої
позначки, тож обидві проблеми зникають. Тому крок 5 обовʼязковий до будь-якого підняття concurrency чи
реплік stream.

Окремо про статус машини: `machineConnected` уже лежить у кожному рядку й оновлюється одним
`updateMany` на машину. `DeviceStatus.CONNECTED = {ONLINE, OFFLINE}`, тож перехід online↔offline
перепроєкції не запускає — лише архівація, виведення з обслуговування чи видалення. Онлайн-статус у рядки
`device_software` не кладемо: кожне мерехтіння машини перераховувало б сотні її тайтлів і CVE.
Фільтр «тільки онлайн» робити на читанні.

## 8. Відкриті питання / що перевірити

- ✅ **Партиціювання Kafka й паралельність споживача** (перевірено 2026-11-09): ключ — `(host_id, software_id)`,
  3 партиції; stream — 1 репліка, concurrency не задано (1 потік). Сьогодні послідовно; див. розділ 7.1.
- ✅ **Очікувані розміри когорт** (2026-11-09): найбільші тенанти — 242, 231, 214, 141, 107 активних девайсів.
  Згортання поки не потрібне; умова його вмикання — розділ 7.1, крок 5.
- **Сигнал виведення пристрою**: яка подія (якщо є) уже існує в OpenFrame при архівації/видаленні пристрою,
  до якої пайплайн може підʼєднатися для G3.
- **Backfill**: початкове завантаження `device_software` для наявних хостів до перемикання прапорця —
  шлях подій цього не покриває.
