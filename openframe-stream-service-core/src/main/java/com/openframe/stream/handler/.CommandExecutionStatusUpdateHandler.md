Handles Debezium stream events for completed RMM command executions, transitioning a `CommandExecution` document from `RUNNING` to `SUCCESS` or `FAILED` in MongoDB by applying the agent's result payload (stdout, stderr, exit code, etc.).

## Key Components

| Member | Description |
|---|---|
| `handle()` | Entry point — extracts `executionId`/`machineId` from `payload.after`, looks up the `CommandExecution` row, and delegates to `applyResult()` |
| `applyResult()` | Guards against overwriting a terminal status, maps result fields onto the document, and persists via `CommandExecutionRepository` |
| `decideStatus()` | Returns `FAILED` if `timedOut=true`, `exitCode != 0`, or a non-blank `error` is present; otherwise returns `SUCCESS` |
| `truncate()` | Clips stdout/stderr to `CommandExecution.MAX_OUTPUT_BYTES` on UTF-8 codepoint boundaries, setting a `*Truncated` flag |
| `Truncated` | Private record pairing the (possibly clipped) string value with a boolean truncation flag |
| `getDestination()` | Declares routing to `Destination.MONGO_COMMAND_HISTORY` |
| `getType()` | Returns `EventHandlerType.COMMON_TYPE` |

## Usage Example

```java
// Wired automatically by Spring — no manual instantiation needed.
// The stream router dispatches COMMAND_EXECUTED events to this handler
// based on Destination.MONGO_COMMAND_HISTORY.

// Typical flow:
// 1. Agent publishes COMMAND_EXECUTED result to the Debezium stream.
// 2. Router calls handle() with the deserialized message.
// 3. Handler looks up the CommandExecution row by (machineId, executionId).
// 4. applyResult() transitions status and writes output fields.
// 5. Saved row is later served by getBatchResults().
```

## Notes

- **Idempotency guard**: `applyResult()` refuses to overwrite a document already in a terminal state — handles duplicate frames and watchdog races.
- **Lookup key**: Uses `(machineId, executionId)` without `tenantId`, matching `CommandResultDeserializer` because the command pipeline runs pre-tenant-enrichment.
- **Double-write**: Runs concurrently with the Cassandra `command_results` write; neither blocks the other.
