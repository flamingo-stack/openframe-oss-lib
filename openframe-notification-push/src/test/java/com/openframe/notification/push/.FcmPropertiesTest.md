Unit tests for `FcmProperties`, verifying that FCM configuration validation correctly rejects invalid or unsafe property values and that misconfigured beans fail at Spring context startup rather than at runtime.

## Key Components

| Test | What It Verifies |
|---|---|
| `defaults_fit_the_payload_limit` | Shipped defaults pass validation without exception |
| `missing_project_id_is_rejected` | `validate()` throws `IllegalStateException` when `project-id` is unset |
| `negative_budget_is_rejected` | Negative byte budget values are rejected with a clear message |
| `overflowing_budget_sum_is_still_rejected` | `Integer.MAX_VALUE` body budget is caught before integer overflow can bypass the limit check |
| `oversized_budget_is_rejected` | A body budget that alone exceeds FCM's 4096-byte limit is rejected and named in the error |
| `spring_fails_the_context_at_startup_rather_than_on_the_first_push` | A misconfigured context fails fast via `PushAutoConfiguration`, not lazily on the first push |

## Usage Example

```java
// Simulate the happy-path default configuration
FcmProperties properties = new FcmProperties();
properties.setProjectId("flamingo-271f8");
properties.validate(); // no exception

// Trigger a budget overflow guard
FcmProperties overflow = new FcmProperties();
overflow.setProjectId("flamingo-271f8");
overflow.setMaxBodyBytes(Integer.MAX_VALUE);
overflow.validate(); // throws IllegalStateException: "do not fit FCM's 4096-byte limit"
```

## Notes

- Tests use `ApplicationContextRunner` to exercise Spring's bean lifecycle, ensuring validation is wired to startup via `PushAutoConfiguration` rather than deferred to the first outbound push.
- All validation errors produce `IllegalStateException` with human-readable messages naming the offending field or budget value, making misconfiguration diagnosable in logs at deploy time.
