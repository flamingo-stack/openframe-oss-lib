Application-level service managing RMM script execution records — persisting, retrieving, and paginating `ScriptExecution` documents stored in MongoDB, with tenant scoping resolved automatically via `TenantIdProvider`.

## Key Components

| Method | Description |
|---|---|
| `findById(String id)` | Non-throwing tenant-scoped lookup by Mongo `_id`; backs Relay `node(id)` refetch |
| `create(...)` | Persists a single `RUNNING` execution row before NATS dispatch |
| `createBatch(...)` | Bulk-persists one `RUNNING` row per target machine under a shared `executionId` |
| `getBatchResults(...)` | Reads back current execution rows for a batch dispatch by `executionId` + machine list |
| `list(...)` | Cursor-paginated, filterable execution history for a single script (Script Details → Execution History tab) |
| `buildRunningRow(...)` | Private builder producing a tenant-scoped `ScriptExecution` in `RUNNING` state |

## Usage Example

```java
// Single ad-hoc execution
ScriptExecutionResponse response = scriptExecutionService.create(
    executionId,
    scriptId,
    machineId,
    PrivilegeLevel.ADMIN,
    30,
    "user@example.com"
);

// Batch execution across multiple machines
List<ScriptExecutionResponse> batchRows = scriptExecutionService.createBatch(
    executionId,
    scriptId,
    scheduleId,
    List.of("machine-1", "machine-2"),
    PrivilegeLevel.STANDARD,
    60,
    "scheduler"
);

// Paginated execution history
CountedGenericQueryResult<ScriptExecutionResponse> history = scriptExecutionService.list(
    scriptId,
    filterInput,
    searchTerm,
    sortInput,
    CursorPaginationCriteria.forward(20, cursor)
);
```

> **Note:** Script display names are resolved at read time via GraphQL field resolvers rather than being stored on each row — renaming a script is automatically reflected across all history entries without backfilling data.
