A vertical list whose items are reordered by dragging a handle, built on Pragmatic drag and drop.
**The one sortable-list implementation in the stack** — every ordered list (schedule scripts,
ticket statuses, AI quick actions via `TicketStatusConfigList`) runs on it; `@dnd-kit` is gone.

The HTML5 drag-and-drop API this is built on does not fire under touch — which is why those lists
once went back to `@dnd-kit`. The answer now is not a second library: on touch/narrow viewports
(`useDragAndDropEnabled()` is `false`) **no drag is initialized at all**, and each row renders an
explicit up/down `SortableMoveButtons` pair instead of its handle. Explicit buttons because on
touch nothing else survives contact with the page: a drag fights scrolling, long-press fights the
context menu.

Deliberately **not** the ticket board, which moves cards between columns and needs a different
model.

## Key Components

| Export | Description |
|---|---|
| `SortableList` | The container. Owns the geometry, the drag monitor and the live region |
| `useSortableItem` | Registers one item: gives back `itemRef`, `dragHandleProps`, `isDragging` and `dragAndDropEnabled` |
| `SortableMoveButtons` | The touch fallback: a joined up/down pair, disabled at the ends, announcing through the list's live region |
| `SLOT_STICKINESS` | The dead band around a slot boundary, as a share of one slot's travel |

## Usage

```tsx
<SortableList onReorder={move} getItemLabel={i => rows[i].name} className="flex flex-col gap-6">
  {rows.map((row, i) => <Row key={row.id} row={row} index={i} count={rows.length} />)}
</SortableList>

function Row({ row, index, count }) {
  const { itemRef, dragHandleProps, isDragging, dragAndDropEnabled } = useSortableItem()
  return (
    <div ref={itemRef} className={isDragging ? 'border-ods-accent shadow-lg' : 'border-ods-border'}>
      {dragAndDropEnabled ? (
        <button type="button" {...dragHandleProps} aria-label="Reorder…"><DraggerIcon /></button>
      ) : (
        <SortableMoveButtons index={index} count={count} label={row.name} />
      )}
      …
    </div>
  )
}
```

`onReorder(from, to)` fires **once**, on drop or on an arrow key — never mid-drag. Do not put a
`style` prop on the item's root: the list writes `transform` straight onto that node.

## Why it is built this way

- **The drag moves nothing but transforms.** The dragged item keeps its slot and is translated to
  follow the pointer; the items it passes are translated by exactly its height plus the row gap.
  Layout is untouched, so the height of the page around the list cannot move, and the slide is safe
  to animate. Opening and closing real space (margins, `display: none`) is not: interrupt one of
  those transitions by moving the pointer, or reorder the DOM on drop, and the two ends run at
  different rates and the page jumps by an item's height. Both failure modes were measured before
  this shape was settled on.
- **The native drag image is off.** The browser draws it washed out and offers no way to style it,
  so the real item follows the pointer instead, at full opacity.
- **Nearest resting place, with a handicap.** Where a drop would land is whichever slot the item is
  nearest to coming to *rest* in — dnd-kit's `closestCenter`, which flips at the midpoint between
  two slots, so half an item of travel is enough. The slot already held keeps a `SLOT_STICKINESS`
  handicap; without it the item sits exactly ON the boundary it just crossed, so leaving costs half
  an item and returning costs a pixel. Rules and arithmetic live in `slot-geometry.ts`, pure and
  unit-tested (`src/__tests__/sortable-slot-geometry.test.ts`).
- **Everything is measured once, at drag start,** so an item moving out of the way can never change
  the answer that moved it and start an oscillation. No React state changes during a drag: the
  transforms are written straight to the DOM, so dragging a list of form cards re-renders nothing.
- **The landing is a FLIP, so the data never waits for it.** `onReorder` fires immediately; the
  animation runs in a layout effect after the commit that carries the reorder, reading where each
  item *looked* a moment earlier and playing it back from there. Items that stood aside during the
  drag come out with a delta of zero — they are already in place — so this animates the dropped item
  and nothing else. Worth animating because the item follows the pointer while the slot flips at a
  midpoint, so it can be released up to half an item away from where it lands; teleporting that far
  reads as a glitch rather than as "done".
- **Auto-scroll is registered on every scrollable ancestor, and the window.** dnd-kit walked that
  chain for you; Pragmatic makes each scroller opt in by name, so after the migration a drag towards
  the edge of the screen scrolled nothing. The window alone is not enough either — the app's real
  scroller is the layout's `<main>`. Because an ancestor can now scroll mid-drag, every position is
  measured relative to the list's own top rather than to the viewport or the document, so a scroll
  moves the list and the pointer together and nothing goes stale.
- **Keyboard.** Pragmatic drag and drop ships none, so `dragHandleProps` carries Arrow Up / Arrow
  Down — one press, one move. The list announces every move through its own live region.
- **Input gating.** `useDragAndDropEnabled()` — `(pointer: fine) and (hover: hover) and
  (min-width: 800px)` — decides whether any drag exists. `false` (touch, narrow windows, and SSR /
  first render) skips every Pragmatic registration; `SortableMoveButtons` go through the same
  `reorder` as a drop, so the announcement and the `onReorder` contract are identical on every
  input. The consumer `disabled` prop still switches everything off, buttons included.
