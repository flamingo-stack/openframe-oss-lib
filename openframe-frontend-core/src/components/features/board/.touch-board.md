The board for touch and narrow viewports: full-height lanes in a horizontal scroll-snap track, one mostly filling the viewport with the next lane peeking in from the right, switched by swiping — per the tickets Figma mocks, which render no separate column navigation. Rendered by `Board` (`board.tsx`) whenever `DRAG_AND_DROP_MEDIA_QUERY` does not match — it is not exported from the barrel and hosts never pick it directly.

## Key Components

| Export | Description |
|---|---|
| `TouchBoard` | The pager — same `BoardProps` as the drag board, so the mode swap needs no host wiring |

## Key Behaviors

- **No DnD exists here** — every lane renders with `touchMode` (see `board-column.tsx`): no monitor, no drop targets, no `autoScrollColumn`, no keyboard lift, cards forced non-draggable. The HTML5 drag events Pragmatic builds on never fire under touch, so a drag board here is dead affordances stapled to 400px lanes. `onChange` is never called — a card's column is changed from the ticket itself (its dialog), not from the board
- **Pager** — lanes sit in a `snap-x snap-mandatory` track, each `snap-start` at `min(400px, 100% - 2 gutters)` wide, so the current lane left-aligns with the page padding and the next lane peeks in from the right (the peek IS the column navigation). Lane internals are untouched: per-column load-more, skeletons, empty states and header actions (add / archive / tooltip, dense-sized as on desktop per the mock) all keep working
- **Collapse works as on the drag board** — same lane-header buttons, same `collapseStorageKey` (the choice survives a mode switch); a collapsed lane is a narrow vertical stop in the same snap track. Only the custom horizontal scrollbar is absent — in a snap pager the track itself is the navigation

## Usage

Not used directly — render `<Board>` and the mode picks itself. See `.board.md`.
