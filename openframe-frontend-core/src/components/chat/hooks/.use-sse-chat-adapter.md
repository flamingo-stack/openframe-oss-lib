The hub's chat on the one chat engine (`useChatEngine`): its stream transport, its history and its conversation list, read from the ambient `ChatRuntime`. Every rule about a turn, an approval and the thread is the engine's (`engine/use-stream-turns.ts`, the reducer).

## Exports

- **`sseChatTransport(endpoints)`**: the hub's chat endpoint as a `ChatStreamTransport`. A turn is a POST to `chatStreamUrl` whose response is the UI message stream; a message carries only the newest user message (the server re-reads `chat_messages` by conversation id), an approval the card's message holding the answered parts. A 4xx is `ChatTurnRefused` with the server's words; a 5xx is not a refusal (it may be a gateway's word about a write still running). The conversation id the server mints is read off `message-metadata` / `start` / `finish` chunks (`dialogIdOf`).
- **`hubChatHistory({ historyUrl, conversationsUrl })`**: the transcript (`GET <historyUrl>?conversationId=`, one page, rows through `messageOfStoredRow`, `found: false` on an empty answer is `missing`), and with a conversations endpoint the list, archive, rename and restore (`createChatConversationsApi`).
- **`useSseEngineConfig(options, active)`**: the engine configuration from the runtime: the transport, the history, the remembered conversation id (`chat-conversation-storage`, the only local state), the slash-command catalog a card's Display runs, `tableIdForDocumentType` and `emptyListSkipsToCompose`.
- **`useSseChatAdapter(options, { active })`**: `useChatEngine(useSseEngineConfig(...))`.

## Contracts

- `source` is read from the runtime, never sent on the wire: the hub resolves it server-side.
- `tableIdForDocumentType` defaults to `defaultTableIdForDocumentType`, so Ask (narrowed retrieval) and Display work in embedders without wiring.
- Without `chatConversationsUrl` the chat is one thread: `dialogCapabilities` is absent and the minted conversation id is never shown (`activeDialogId` null).
