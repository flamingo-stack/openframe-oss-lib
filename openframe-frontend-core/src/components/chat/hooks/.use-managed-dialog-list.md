The ONE dialog-list state machine shared by both transport adapters — NATS/Mingo managed-dialog mode and the SSE/Guide adapter when `ChatRuntime.endpoints.chatConversationsUrl` is set. The Chat Archive page keeps its own local pager in `useChatDialogManager`, deliberately untouched. Extracted from `useNatsChatAdapter` so Guide mode reuses the exact list/paging/mutation semantics openframe-frontend already relies on.

## Key Components

### `useManagedDialogList(args)`
Owns the loaded `DialogItem[]` page, the server cursor, first-page loading/error state (with the retry re-arm), cursor pagination, an optional server-side `search` term (a change re-runs page 1) and the optimistic rename / archive / delete mutations. Does NOT own the active dialog id, message history or the transport — the adapters layer those on top via `onDialogRemoved`.

### `UseManagedDialogListArgs`
- `autoLoad` — gates the AUTOMATIC first-page load only; the adapters pass their own `active` gate so an idle transport does no network
- `fetchDialogs` / `renameDialog` / `archiveDialog` / `deleteDialog` — host callbacks; presence IS the capability (absent = inert / no-op)
- `pageSize` — sent as `limit`
- `search` — `undefined` = no search support (NATS keeps `{cursor, limit}` wire params); any string change reloads page 1 with `search`
- `onDialogRemoved(id, 'archived' | 'deleted')` — fires AFTER the local removal, read through a latest-ref
- `logTag` — console prefix for failure logs

### `UseManagedDialogListResult`
`dialogs`, `dialogsNextCursor`, `isDialogsLoading`, `dialogsError`, `hasMoreDialogs`, `loadDialogsPage`, `reloadDialogs`, `loadMoreDialogs`, `renameDialog`, `archiveDialog`, `deleteDialog`, plus `upsertDialogTop(item)` (prepend + dedupe) and `bumpDialogToTop(id)` (re-head with a fresh timestamp, matching the server's `last_message_at desc`).

## Behavioural contracts

- `isDialogsLoading` reads true from the FIRST render whenever a first page is coming (and again synchronously on every search change, including clearing one), so a consumer branching on "the list is empty" never sees a settled-and-empty frame before the request starts.
- A monotonic request id means only the LATEST page-1 load may touch the list, cursor or flags — search-as-you-type, the end-of-turn refresh and an unarchive all overlap, and without it the last-resolving response wins.
- Appends dedupe by id: a row whose `last_message_at` moved between page fetches can come back on a later page.
- Only the FIRST page failing sets `dialogsError`; a pagination failure keeps the loaded rows.
- Archive and delete failures are logged AND re-thrown, so `useChatDialogManager.handleConfirmArchive` (which awaits and catches) can keep its modal open for a retry instead of closing over a write the server rejected. Rename is the exception: it is logged and SWALLOWED after rolling its optimistic title back, matching the pre-extraction NATS adapter, because `handleConfirmRename` fires it as `void renameDialog(...)` and a rejection would only surface as an unhandled rejection.
- Rename is optimistic; the rollback title is read synchronously from a live ref at call time (capturing it inside a `setState` updater was unreliable — the updater may run after an immediately-rejecting callback reaches the catch).
