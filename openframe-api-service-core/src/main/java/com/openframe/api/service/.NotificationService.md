Handles paginated retrieval of notifications for a given recipient, supporting cursor-based pagination, read-status filtering, search, and sort direction.

## Key Components

| Member | Description |
|---|---|
| `list(...)` (2 overloads) | Fetches a paginated, filtered list of `NotificationView` results for a recipient. The second overload accepts an optional `SortInput`. |
| `normalizeSearch(String)` | Trims and nullifies search strings shorter than `SEARCH_MIN_LENGTH` (2 chars). |
| `resolveSortDirection(SortInput)` | Resolves sort direction from input; warns on invalid sort fields and falls back to `DESC`. |
| `buildPageInfo(...)` | Constructs cursor-based `PageInfo` with `hasNextPage`, `hasPreviousPage`, `startCursor`, and `endCursor`. |
| `ALLOWED_SORT_FIELDS` | Restricts sorting to `"id"` and `"createdAt"`. |

## Usage Example

```java
// Inject the service
@Autowired
private NotificationService notificationService;

// Build filter and pagination
NotificationFilter filter = new NotificationFilter(/* read= */ false, /* search= */ "alert");
CursorPaginationCriteria pagination = CursorPaginationCriteria.of(10, null, false);
SortInput sort = new SortInput("createdAt", SortDirection.DESC);

// Fetch paginated notifications for a user
GenericQueryResult<NotificationView> result = notificationService.list(
    "user-123",
    RecipientType.USER,
    filter,
    pagination,
    sort
);

result.items().forEach(n -> System.out.println(n.id() + " read=" + n.isRead()));
System.out.println("hasNextPage: " + result.pageInfo().hasNextPage());
```

## Notes

- Cursor encoding uses `CursorCodec.encode(id)` derived from the first/last item IDs.
- Backward pagination reverses the result list after slicing.
- The `limit + 1` fetch pattern is used to detect whether a next/previous page exists without a separate count query.
