Manages proactive JWT access token refresh in a background Tokio task, ensuring the shared token stays valid before expiry without requiring a NATS reconnect. Refresh timing is taken from the token's own lifetime and kept on a suspend-aware monotonic clock; the device wall clock plays no part in scheduling, so a skewed or stepping clock cannot make the agent refresh early, late, or in a loop.

## Key Components

**`TokenRefreshRunManager`** — Cloneable struct holding references to `AgentAuthService` and `DeactivationService`.

- **`new()`** — Constructs the manager with the required service dependencies.
- **`start()`** — Spawns a background Tokio task that refreshes once immediately (the stored token's remaining life is unknowable without trusting the device clock, and `shared_token.enc` must be valid before the tools connect), then loops: wait for the current `RefreshSchedule`, call `reauthenticate()` with a timeout, retry on failure, reschedule from the response.

**`boot_clock`** *(private module)* — Time since boot on a clock that keeps counting through sleep and hibernation: `CLOCK_BOOTTIME` on Linux, `CLOCK_MONOTONIC` on Apple platforms (which, unlike `CLOCK_UPTIME_RAW` behind `Instant`, counts sleep), and `Instant`/`QueryPerformanceCounter` elsewhere (documented by Windows as counting through standby and hibernation).

**`RefreshSchedule`** *(private)* — the single deadline `due` on the boot clock: the token's lifetime minus the lead, counted from the moment the refresh request was sent. `wait()` sleeps in `wait_slice` slices and re-reads the boot clock after each, because tokio timers run on `Instant` and stand still through sleep on macOS/Linux; a nap therefore costs at most one slice of lateness.

**`schedule_after_refresh()`** *(private)* — Builds the schedule from a token response: lifetime = the shorter of `expires_in` and `exp − iat` (either alone if only one is present), else `fallback_interval`; capped at `max_ttl`; delay = lifetime − lead, floored at `min_interval` (the hot-loop guard). Measures the device-vs-server clock skew as `now − iat` for a warning at or above `SKEW_WARN`; that is the only wall-clock read.

**`RefreshTiming`** *(private)* — the timing knobs; production values via `Default`, shrunk to milliseconds by the tests (`with_timing`, defined in the test file) so the real loop can be run against a mock token endpoint:

| Field | Default | Purpose |
|---|---|---|
| `margin` | 5 min | Refresh this early before `exp` |
| `min_lead` | 30 s | Lead for short-lived tokens |
| `fallback_interval` | 30 min | Used when the token lifetime is unknown |
| `max_ttl` | 24 h | Cap on a lifetime read from the token |
| `min_interval` | 60 s | Floor between two refreshes (hot-loop guard) |
| `wait_slice` | 60 s | Boot-clock re-check period while waiting |
| `retry_interval` | 60 s | Delay between failed refresh retries |
| `reauth_timeout` | 30 s | Cap per `reauthenticate()` call |

`SKEW_WARN` (5 min) is the clock skew that gets logged.

## Usage Example

```rust
let manager = TokenRefreshRunManager::new(auth_service.clone(), deactivation_service.clone());

// Spawns a background task; call once at agent startup.
manager.start();
```

The task refreshes once at start, then wakes `margin` before the token's lifetime runs out (measured on the boot clock from the moment the request was sent), calls `reauthenticate()`, and retries every `retry_interval` on failure. Short-lived tokens (TTL ≤ `margin`) use `min_lead`; two refreshes are never closer than `min_interval`.
