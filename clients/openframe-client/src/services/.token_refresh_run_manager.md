Manages proactive JWT access token refresh in a background Tokio task, ensuring the shared token stays valid before expiry without requiring a NATS reconnect. Refresh timing is taken from the token's own lifetime, not from the device clock, so a skewed clock cannot make the agent refresh in a loop.

## Key Components

**`TokenRefreshRunManager`** — Cloneable struct holding references to `AgentAuthService`, `AgentConfigurationService` and `DeactivationService`.

- **`new()`** — Constructs the manager with the required service dependencies.
- **`start()`** — Spawns a background Tokio task that loops indefinitely, waiting for the current `RefreshSchedule`, then calls `reauthenticate()` with a timeout, retrying on failure and rescheduling from the response.

**`RefreshSchedule`** *(private)* — When the next refresh is due; the same delay is stamped on both clocks (`after(now_mono, now_wall, delay, floor)`):

- `due_at` — monotonic deadline (`tokio::time::Instant`): the token's lifetime minus the lead, counted from receipt. Immune to wall-clock jumps.
- `due_wall` — the same deadline in device wall-clock seconds. Catches a resume from suspend, where the monotonic clock may have stood still.
- `not_before` — floor: never refresh again sooner than `MIN_INTERVAL` after the previous refresh, whatever either clock says.
- `wait()` — sleeps in `WAIT_SLICE` slices until `due_at` or `due_wall` is reached (and `not_before` has passed).

**`schedule_after_refresh()`** *(private)* — Builds the schedule from a token response: lifetime = `expires_in`, else `exp − iat` from the JWT, else `FALLBACK_INTERVAL`; capped at `MAX_TTL`. Measures the device-vs-server clock skew as `now − iat` and logs a warning at or above `SKEW_WARN`.

**`schedule_for_existing()`** *(private)* — For the token found at startup (receipt time unknown): the device clock estimates the remaining life within the token's own lifetime. An expired-looking token, a token with more life left than it ever had (clock provably behind) or one without `iat` refreshes at once — a skewed clock costs at most one early refresh.

**`RefreshTiming`** *(private)* — the timing knobs; production values via `Default`, shrunk to milliseconds by the tests (`with_timing`) so the real loop can be run against a mock token endpoint:

| Field | Default | Purpose |
|---|---|---|
| `margin` | 5 min | Refresh this early before `exp` |
| `min_lead` | 15 s | Lead for short-lived tokens |
| `fallback_interval` | 30 min | Used when the token lifetime is unknown |
| `max_ttl` | 24 h | Cap on a lifetime read from the token |
| `min_interval` | 60 s | Floor between two refreshes (hot-loop guard) |
| `wait_slice` | 60 s | Wall-clock re-check period while waiting |
| `retry_interval` | 60 s | Delay between failed refresh retries |
| `reauth_timeout` | 30 s | Cap per `reauthenticate()` call |

`SKEW_WARN` (5 min) is the clock skew that gets logged.

## Usage Example

```rust
let manager = TokenRefreshRunManager::new(
    auth_service.clone(),
    config_service.clone(),
    deactivation_service.clone(),
);

// Spawns a background task; call once at agent startup.
manager.start();
```

The task wakes `margin` before the token's lifetime runs out (measured from the moment the token was received), calls `reauthenticate()`, and retries every `retry_interval` on failure. Short-lived tokens (TTL ≤ `margin`) use `min_lead`; two refreshes are never closer than `min_interval`.
