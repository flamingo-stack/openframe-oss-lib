Manages proactive JWT access token refresh in a background Tokio task, ensuring the shared token stays valid before expiry without requiring a NATS reconnect. Refresh timing is taken from the token's own lifetime, not from the device clock, so a skewed clock cannot make the agent refresh in a loop.

## Key Components

**`TokenRefreshRunManager`** — Cloneable struct holding references to `AgentAuthService`, `AgentConfigurationService` and `DeactivationService`.

- **`new()`** — Constructs the manager with the required service dependencies.
- **`start()`** — Spawns a background Tokio task that loops indefinitely, waiting for the current `RefreshSchedule`, then calls `reauthenticate()` with a timeout, retrying on failure and rescheduling from the response.

**`RefreshSchedule`** *(private)* — When the next refresh is due:

- `due_at` — monotonic deadline (`tokio::time::Instant`): the token's lifetime minus the lead, counted from receipt. Immune to wall-clock jumps.
- `due_wall` — device wall-clock deadline (`exp − lead`, corrected by the measured clock skew). Catches a resume from suspend, where the monotonic clock may have stood still.
- `not_before` — floor: never refresh again sooner than `MIN_INTERVAL` after the previous refresh, whatever either clock says.
- `wait()` — sleeps in `WAIT_SLICE` slices until `due_at` or `due_wall` is reached (and `not_before` has passed).

**`schedule_after_refresh()`** *(private)* — Builds the schedule from a token response: lifetime = `expires_in`, else `exp − iat` from the JWT, else `FALLBACK_INTERVAL`. Measures the device-vs-server clock skew as `now − iat` and logs a warning above `SKEW_WARN`.

**`schedule_for_existing()`** *(private)* — For the token found at startup (receipt time unknown): the device clock estimates the remaining life, clamped to `[0, ttl]`, so a skewed clock costs at most one early refresh.

**Timing constants:**

| Constant | Value | Purpose |
|---|---|---|
| `REFRESH_MARGIN` | 5 min | Refresh this early before `exp` |
| `MIN_LEAD` | 15 s | Lead for short-lived tokens |
| `FALLBACK_INTERVAL` | 30 min | Used when the token lifetime is unknown |
| `MIN_INTERVAL` | 60 s | Floor between two refreshes (hot-loop guard) |
| `WAIT_SLICE` | 60 s | Wall-clock re-check period while waiting |
| `SKEW_WARN` | 5 min | Clock skew that gets logged |
| `RETRY_INTERVAL` | 60 s | Delay between failed refresh retries |
| `REAUTH_TIMEOUT` | 30 s | Cap per `reauthenticate()` call |

## Usage Example

```rust
let manager = TokenRefreshRunManager::new(
    auth_service.clone(),
    config_service.clone(),
    deactivation_service.clone(),
);

// Spawns a background task; call once at agent startup.
manager.start();
```

The task wakes `REFRESH_MARGIN` before the token's lifetime runs out (measured from the moment the token was received), calls `reauthenticate()`, and retries every 60 s on failure. Short-lived tokens (TTL ≤ `REFRESH_MARGIN`) use `MIN_LEAD`; two refreshes are never closer than `MIN_INTERVAL`.
