Reactive MongoDB repository interface for `User` documents, providing non-blocking query methods using Project Reactor's `Mono` type for single-value async responses.

## Key Components

| Method | Return Type | Description |
|---|---|---|
| `findByEmail(String email)` | `Mono<User>` | Looks up a user by email address |
| `existsByEmail(String email)` | `Mono<Boolean>` | Checks if an email is already registered |
| `existsByEmailAndStatus(String email, UserStatus status)` | `Mono<Boolean>` | Checks if an active (or other status) user exists for an email |
| `existsByTenantIdAndId(String tenantId, String id)` | `Mono<Boolean>` | Scopes user existence check by tenant — used in shared/SaaS contexts where tenant isolation must be explicit |

**Extends:**
- `ReactiveMongoRepository<User, String>` — full reactive CRUD via Spring Data MongoDB
- `BaseUserRepository<Mono<User>, Mono<Boolean>, String>` — shared contract ensuring consistency with blocking counterpart

## Usage Example

```java
@Service
public class UserService {

    private final ReactiveUserRepository userRepository;

    public UserService(ReactiveUserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public Mono<User> getUserByEmail(String email) {
        return userRepository.findByEmail(email);
    }

    public Mono<Boolean> isUserInTenant(String tenantId, String userId) {
        return userRepository.existsByTenantIdAndId(tenantId, userId);
    }
}
```

## Notes

- The `existsByTenantIdAndId` method uses tenant-first parameter ordering intentionally — callers on the shared/SaaS layer must scope queries by tenant explicitly rather than relying on ambient context.
- All methods return `Mono` (never `Flux`), reflecting single-result semantics appropriate for user lookups.
